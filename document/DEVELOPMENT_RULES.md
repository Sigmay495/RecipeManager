# レシピ管理アプリ 開発ルール

## 1. 目的

本プロジェクトでは、レシピ管理アプリをドキュメント駆動で開発する。
各工程の成果物をレビューし、承認を得てから次の工程へ進む。

## 2. ディレクトリ構成

- `AGENTS.md`: 新しい開発セッションが最初に参照する作業ガイドを格納する。
- `document/`: 要件定義書、設計書などのドキュメントを格納する。
- `src/`: アプリケーションのソースコードを格納する。
- `dst/`: アプリケーションが生成する出力ファイルを格納する。

## 3. 開発工程

初期開発は以下の順序で進める。

1. 要件定義
2. 概要設計
3. 詳細設計
4. コーディング
5. テスト
6. リリース

工程の順序を変更したり、工程を省略したりしない。

v1.00以降の変更は、規模にかかわらず以下の順序で進める。

1. 変更内容と影響範囲の確認
2. 要件定義書・設計書の更新要否の判断と、必要な文書の更新
3. コーディング
4. テストおよびテスト報告書の更新
5. ユーザーレビュー
6. リリース

不具合修正であっても、仕様または設計に影響する場合は該当文書を先に更新する。

## 4. レビューと承認

- 各工程で成果物を作成した時点で作業を止め、ユーザーへレビューを依頼する。
- ユーザーから明示的な承認または次工程へ進む指示を受けるまで、次の工程には着手しない。
- レビューで修正依頼があった場合は、対象の成果物のみを修正し、再度レビューを依頼する。
- 不明点や、判断によって仕様・設計が変わる事項は、独断で決定せずユーザーへ確認する。

## 5. Git・GitHubの運用

- ユーザーから明示的な指示がない限り、GitHubへPushしない。
- コミット、ブランチ操作、Pull Requestの作成など、その他のGit操作もユーザーの指示に従う。
- Git操作を行う場合は、対象と内容を確認してから実行する。
- Push前に、ローカル設定、キャッシュ、APK、署名鍵、認証情報などが追跡対象に含まれていないことを確認する。
- APKおよびAABはGitのソース管理へ含めない。配布が必要な場合は、ユーザーの指示を受けてGitHub Releaseなどへ添付する。

## 6. 作業範囲

- 指示された工程および成果物の範囲内だけを作業する。
- 将来工程の実装や文書を先回りして作成しない。
- 既存の成果物を変更する際は、ユーザーの意図と既存内容を尊重する。

## 7. バージョン管理

- 表示バージョンは `vメジャー.マイナー` 形式とする。
- 不具合修正や小規模な改善では末尾を1増やす。例: `v1.00` → `v1.01`。
- 後方互換性のある機能追加では小数第1位を増やす。例: `v1.01` → `v1.10`。
- 大きな仕様変更や後方互換性のない変更では整数部を増やす。例: `v1.10` → `v2.00`。
- Androidの`versionCode`はリリースごとに必ず増加させ、同じ値を再利用しない。
- README、CHANGELOG、アプリのバージョン、テスト報告書、Gitタグの表記を一致させる。

## 8. テスト・品質確認

リリース前に、変更範囲に応じて次を実施する。

- JVM単体テスト
- Android端末テスト
- Android Lint
- APKまたはAABの生成
- 主要画面と変更機能の動作確認
- オフライン起動確認
- バックアップ・復元確認
- 既存データを保持した上書き更新確認

省略する項目がある場合は、理由と未確認範囲をユーザーへ報告する。結果は `document/TEST_REPORT.md` へ記録し、問題が残る状態でリリースしない。

## 9. データ互換性

- Roomデータベース、JSON Schema、Import形式、バックアップ形式を変更する場合は、既存データへの影響を事前に確認する。
- DB構造を変更する場合は移行処理を用意し、安易な破壊的再作成を行わない。
- バックアップ形式を変更する場合は、旧版の読込可否と変換方法を設計書へ記載する。
- データ変更を伴う更新では、更新前のバックアップを利用者へ案内する。

## 10. リリース運用

- プロジェクト本体はMIT Licenseで公開し、著作権者表記は`Sigmay495`とする。
- 依存ライブラリのライセンスとNOTICEは `THIRD_PARTY_NOTICES.md` で管理し、依存関係を変更した場合は内容を見直す。
- 日常利用向けの配布物は、固定した署名鍵で署名したRelease APKまたはAABとする。
- 署名鍵と認証情報はリポジトリへ登録せず、安全な別媒体で管理する。
- Debug APKは開発・動作確認用途に限定する。
- リリース時はバージョン番号、README、CHANGELOG、テスト報告書、変更内容を確認してからタグを作成する。
- CHANGELOGには、バージョン番号、公開日、追加機能、変更・改善、不具合修正、データ移行・互換性の注意、既知の問題を必要に応じて記録する。
- GitHub Releaseの作成や配布物の添付は、ユーザーから明示的な指示を受けてから行う。
- 具体的なリリース作業は `document/RELEASE_GUIDE.md` に従う。
- 新しい開発環境の構築は `document/DEVELOPMENT_SETUP.md` に従う。
